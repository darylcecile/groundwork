## Behaviour and entrypoints

Groundwork resolves a project and prepares older metadata before selecting its project-owned checks. It combines an optional task plan with active invariants and runs checks against identified source, retaining logs, observations and artifacts before assessing execution and requirement coverage. Each save derives a portable record from the authoritative result. A later local report view or explicit publication reassesses saved evidence, source freshness and receipt identity where present without rerunning checks. Remote PR viewing reads published accounts and their current-head relationship.

The installed `groundwork` entry is `skills/verify-work/verify.mjs` ([package.json — `bin`](../../package.json)). Local entrypoints are `init [directory]`, `view guide [query]`, `map [feature]`, `verify [check ...] [--plan file] [--changed ref] [--base ref] [--fresh]`, and `view report [id]`. Optional GitHub entrypoints are `publish pr [number-or-url] --run <id>` and `view pr [number-or-url]`. Names passed to `verify` are **check IDs**; a feature in the terminal map is a **behaviour ID**.

CLI invocations outside CI register their project with one user-wide portal through [lib/portal.mjs](../../lib/portal.mjs); PR publish/view dispatches before portal startup. The [project registry](../../portal/projects.ts) retains discovery metadata in the user's cache. Its [Hono server](../../portal/server.ts) resolves project-ID-scoped routes and uses the [data adapter](../../portal/data.ts) to read saved external or legacy reports and the merged catalogue. The [React UI](../../portal/ui/main.tsx) provides project selection, receipt/evidence details and an interactive catalogue/map. The portal presents saved statuses and original receipt provenance without the source, evidence or receipt-input reassessment performed by `view report`; project-tagged file events refresh those snapshots. See [Browse the local portal](../guides/browse-the-local-portal.md#browse-the-local-portal) for the journey and verification boundaries.

Relevant journeys are [Adopt a project](../guides/adopt-a-project.md#adopt-a-project), [Plan and select verification](../guides/plan-and-select-verification.md#plan-and-select-verification), [Verify a behaviour and review evidence](../guides/verify-a-behaviour-and-review-evidence.md#verify-a-behaviour-and-review-evidence), [Exercise a driver and compare revisions](../guides/exercise-a-driver-and-compare-revisions.md#exercise-a-driver-and-compare-revisions), and [Verification records](../guides/verification-records.md#verification-records). Relevant catalogue IDs include `adoption`, `catalogue`, `coverage`, `drivers`, `verification-records`, `pr-verification`, and invariant `complete-evidence` ([project catalogue](../verify.d)). The accepted [local-first decision](../decisions/local-first-verification.md) explains the record/publication boundary.

## Flow

```text
CLI
 ├─ view pr → GitHub records + current head/status → history display/exit
 ├─ publish pr --run ID → projectRoot → saved result → reassessRun
 │    → clean pushed-source match → PR artifact/comment + commit status
 └─ local commands → projectRoot → prepareProject
      ├─ loadConfig → view guide / map → catalogue + guide issues
      ├─ verify → loadConfig → task plan + changedFiles? → selectChecks
      │    → active invariants → external run + workspace latest
      │    → runChecks → matching receipt or fresh trial
      │    → assess + incremental result.json/report.md saves → local report
      └─ view report → run ID or workspace latest → saved result
           → reassessRun → display/exit
```

### Project discovery

`projectRoot()` starts at the invocation directory, except that a path inside `.groundwork/` or `.verify/` starts above that metadata namespace. It walks upward to the first recognized project metadata, checking each directory before stopping at a `.git` boundary or filesystem root. Thus `.groundwork/config/verify.json` is not accidentally treated as the adopted project's configuration when invoked there ([skills/verify-work/verify.mjs — `projectRoot`](../../skills/verify-work/verify.mjs)).

`prepareProject(root)` runs before CLI `verify`, guide/report views and `map`; `init` uses its explicit/current directory with `initialize: true`. It normally partitions the active base and authored guide sections into fragments and guides while preserving check order and bindings. Whole-document command inputs move intact into one active guide or fragment, with exact declared paths rewritten. It updates references and retires superseded metadata. The agent resolves project-specific repairs from repository context. New initialization creates a bootstrap, project context, an empty configuration fragment and workflow instructions; it does not invent an executable scenario ([lib/migration.mjs](../../lib/migration.mjs), [lib/guide-migration.mjs](../../lib/guide-migration.mjs)).

The underlying readers remain pure. `configPath(root)` prefers `.groundwork/verify.json`, then root `verify.json`, then `.verify/verify.json`; an invalid preferred base does not trigger fallback. `loadConfig` reads that base and sorted fragments from the current and legacy namespaces without writing files. CLI preparation leaves active fragments under `.groundwork/verify.d/`; repeated preparation is idempotent. The [portal adapter](../../portal/data.ts) uses `loadConfig` directly and does not migrate metadata ([lib/config.mjs](../../lib/config.mjs)).

`prepareEvidenceStore` imports generated `.groundwork/runs`, `.verify/runs` and latest pointers before removing their originals. It preserves conflicting runs separately and accepts identical concurrent imports. Malformed or orphaned old pointers are archived; they do not block fresh verification. Store overlap with legacy runtime directories is rejected. Storage uses `GROUNDWORK_STATE_HOME`, otherwise `$XDG_STATE_HOME/groundwork`, defaulting to `~/.local/state/groundwork`. The namespace combines the Git common directory with the project's relative location, so matching projects in repository worktrees share evidence while each workspace has its own latest pointer ([lib/store.mjs](../../lib/store.mjs)). Migration preserves historical identity and does not create reusable receipts.

`verify` and `view report` require Git for `source()`. Guide and terminal-map inspection do not. Check commands execute from the discovered project root. A local `--plan` input is resolved against the **invocation cwd** and read before preparation; `run` then validates the captured contents, so moving a legacy plan path does not lose the supplied plan ([skills/verify-work/verify.mjs](../../skills/verify-work/verify.mjs)).

### Catalogue and selection

Configuration parsing rejects unknown fields, supplies check defaults, and validates references after base/fragment composition. Duplicate IDs and conflicting context values identify both source files; catalogue rows retain defining-file provenance. Each invariant's ID is added to its enforcing checks' `covers`. Behaviours may have no checks; invariants must name existing checks. Optional `dependsOn` lists are navigational and do not change selection or check bindings. See [lib/config.mjs](../../lib/config.mjs) and the [configuration reference](../../skills/verify-work/references/verification.md#project-configuration).

After preparation, `view guide [query]` searches IDs, descriptions, paths, and behaviour entrypoints case-insensitively. It prints matching entries and checks, then validates those entries' `guide` files/anchors. It executes no check command. Validation checks a safe project-relative Markdown target, including realpath containment and headings/explicit anchors; it does **not** recursively check Markdown links or establish the map's factual accuracy ([lib/config.mjs — `catalogue`, `markdownAnchors`, `catalogueIssues`](../../lib/config.mjs); [CLI — `guide`](../../skills/verify-work/verify.mjs)).

For execution, `selectChecks` unions these reasons, preserving configuration check order:

1. All checks when neither names nor `--changed` are supplied; otherwise explicitly named checks.
2. Every `required` check.
3. With `--changed`, direct check-path matches and matches against covered catalogue paths. Checks without direct or covered catalogue scope remain conservative selections.
4. Checks covering active invariants. Without `--changed`, all invariants are active even for a named run. With it, unscoped invariants remain active and scoped invariants activate on matching paths.
5. Explicit plan-bound checks and checks covering the plan's behaviours. Unknown planned check IDs fail validation.

`changedFiles(root, ref)` resolves a commit and compares it to the working tree, also including non-ignored untracked files. Runtime paths are excluded; selection patterns use `node:path.matchesGlob`. This selects work; it does not perform the separate `--base` comparison. Returned `reasons`, `omitted`, `invariants`, `unmappedPaths`, and `uncoveredBehaviours` are retained in the report. Unmapped paths and uncovered behaviours are planning signals, not automatic failure conditions ([lib/config.mjs — `selectChecks`](../../lib/config.mjs); [lib/runner.mjs — `changedFiles`](../../lib/runner.mjs)).

The CLI validates the task plan before selection and passes it to `selectChecks`. `withInvariants` then adds active invariant requirements. Without names or `--changed`, all checks remain selected even with a plan. Stale catalogue references relevant to selected checks/active invariants enter assessment as problems; commands can still run, but a passing claim cannot result while those problems remain ([CLI — `run`](../../skills/verify-work/verify.mjs)).

### Terminal feature maps

The CLI's `map` command loads the same configuration and passes it to [lib/map.mjs — `renderMap`](../../lib/map.mjs). Without a query it displays all behaviour nodes and their recorded direct outgoing edges. A focused query prefers an exact ID, then requires a unique case-insensitive ID/description match. It displays the focus, its direct dependencies and its direct consumers; it does not expand transitively. Cycles therefore remain finite.

Edges come only from behaviour `dependsOn` lists. The renderer uses `catalogue` for descriptions, source/check/guide metadata, and derives consumers by reversing declared edges. Missing links and metadata are labelled as unrecorded/unmapped. Shared paths or covering checks are not dependency evidence. Navigation does not change verification selection, coverage or invariant enforcement.

The CLI validates guides for the displayed IDs with `catalogueIssues` after printing the diagram. A stale guide leaves the diagram visible and returns exit `2`; ambiguous/unknown queries and flags also return `2`. An empty overview returns explanatory guidance and exit `0`. First-command preparation may convert older metadata and relocate evidence; subsequent map navigation leaves source and latest-run pointers unchanged. Neither view executes a check or creates a verification run ([CLI — `map`](../../skills/verify-work/verify.mjs); [test/verify.test.mjs — feature-map scenarios](../../test/verify.test.mjs)).

### Plan and run snapshot

`validatePlan` freezes the goal and requirement bindings. Optional `review: true` requires an evidence-backed `kind: "review"` observation explicitly covering that requirement ID. `withInvariants` appends required `invariant:<id>` entries and rejects collisions with those IDs. It can create an invariant-only plan when no task plan was supplied ([lib/model.mjs](../../lib/model.mjs)).

Once validation and initial source capture succeed, `run` creates a version-2 result in the external store with pending checks and `finishedAt: null`, then updates its workspace's latest pointer **before execution**. Each save writes authoritative `result.json` and derives `report.md`; an unfinished run cannot be recorded as passed. `runChecks` saves `plan.json`, exposes it to drivers, detects changes/removal during execution, and restores the original snapshot. Its callback saves completed check results, including trials or reused receipt provenance ([CLI — `run`](../../skills/verify-work/verify.mjs); [lib/runner.mjs — `runChecks`](../../lib/runner.mjs)).

An interrupted initialized run supersedes the previous latest run and remains unfinished. Errors before initialization—such as invalid options, configuration, selection, or plan—return exit `2` without creating a new latest report. These are distinct paths.

### Execution and comparison

Before a trial, the runner evaluates the check's opt-in `reuse` contract. Matching includes whole-source content, normalized check definition, engine/runtime, context, frozen plan, declared environment-value digests and explicit input-file content. The latest matching receipt attempt must be complete with intact evidence; a reusable failure remains failed. Reused evidence is copied into the current run with original provenance. `--fresh`, baseline comparisons, repeated trials and setup/cleanup force execution ([lib/receipts.mjs](../../lib/receipts.mjs)).

`runChecks` processes selected checks serially. Each trial receives a fresh `artifacts/` directory, source fingerprint, plan path, and declared context. Optional setup, exercise `command`, and optional cleanup run in separate Bash processes with `-e` and `pipefail`, all from the candidate project root. Shell exports from setup do not persist into the exercise. Failed setup skips exercise; cleanup is attempted in `finally` with no abort signal ([lib/runner.mjs — `executeCommand`, `trial`](../../lib/runner.mjs)).

Drivers receive `GROUNDWORK_EVIDENCE_DIR`/legacy `VERIFY_ARTIFACTS`, `GROUNDWORK_PROJECT_DIR`, `GROUNDWORK_SOURCE_DIR`, phase, trial number, and `GROUNDWORK_PLAN`; the full contract is in [Driver lifecycle and evidence](../../skills/verify-work/references/verification.md#driver-lifecycle-and-evidence). Structured results contribute observations, measurements, and context. Declared artifacts and observation evidence must be nonempty files contained within that trial's evidence directory, including through symlinks. An observation cannot cite its result file directly or through a symbolic-link alias. Evidence and logs are hashed; contradictory declared context or source changes during the trial prevent a clean pass ([lib/model.mjs — `capture`, `inspectObservations`, `inspectDriver`](../../lib/model.mjs); [lib/runner.mjs — `trial`, lines 127–168](../../lib/runner.mjs)).

Exercise exit `0` passes the process stage; `2`, unavailable commands (`126`/`127`), interruption, and launch failures are inconclusive. Other nonzero exercise exits fail. Nonzero setup/cleanup outcomes are inconclusive. `statusOf` gives recorded failures priority over incompleteness. Repetition retains all requested candidate outcomes; a later success cannot erase an earlier failure.

For `--base`, at least one selected check must declare `compare`. A temporary detached worktree provides baseline source; **both phases use the candidate's driver and cwd**, so the driver must target `GROUNDWORK_SOURCE_DIR`. Non-comparison checks run only on the candidate. Regression comparison requires a usable baseline assertion failure and candidate success; measurement comparison uses matching context, declared units/budgets, and median samples. Checkout/cleanup problems remain report problems; baseline removal is attempted in `finally` ([lib/runner.mjs — `baselineCheckout`, `runChecks`](../../lib/runner.mjs); [lib/model.mjs — `compareTrials`](../../lib/model.mjs)). See the existing [comparison journey](../guides/exercise-a-driver-and-compare-revisions.md#exercise-a-driver-and-compare-revisions).

### Saved report reassessment

After project preparation, `report()` opens the external evidence store and chooses the requested run ID or the current workspace's latest pointer. A completing invocation supplies its own ID, so another run cannot replace its result through the latest pointer. Shared `validateLocalRun` validates the saved result; `reassessRun` flags unfinished runs and changed source, and rechecks retained logs/artifacts/observations with `refreshEvidence`. For checks with receipt keys, it also recomputes current receipt identity; changed declared environment values, ignored files, engine, runtime or context can make a prior pass inconclusive with unchanged source. Other checks receive source/evidence reassessment only. It calls `assess`, prints the result and returns its exit code without rewriting the saved result or rerunning commands. Historical results remain readable without `report.md` and retain their original identity ([CLI — `report`](../../skills/verify-work/verify.mjs); [lib/report.mjs — `validateLocalRun`, `reassessRun`](../../lib/report.mjs)).

Coverage links requirements to explicitly bound checks, catalogue coverage, and evidence-backed observations. Missing explicit checks or required behaviour coverage stays **unverified**. Overall status is **passed / 0** only when checks, observations, required coverage, and problems allow it; **failed / 1** takes priority when a failure remains recorded; otherwise status is **inconclusive / 2**. Source, evidence or receipt-input staleness prevents reuse of a success, but does not erase a recorded check failure ([lib/model.mjs — `statusOf`, `coverage`, `assess`, `refreshEvidence`, `exitCode`](../../lib/model.mjs)).

### Saved records and optional publication

`makeRecord` snapshots the run, frozen plan, selection, checks/observations, coverage, provenance, stages and gaps. `renderRecord` produces readable Markdown plus one `groundwork-record:v1` HTML-comment payload containing `{ record, publication }`; `parseRecord` validates that summary shape. `result.json` and retained evidence remain authoritative. Optional plan `decisions` link project-relative Markdown rationale and do not supply coverage ([lib/report.mjs](../../lib/report.mjs)).

`publishPR` requires an explicit local run ID, reconstructs its record from `result.json` and calls the same reassessment used by local reporting. It additionally requires matching source content, a clean current checkout and its revision equal to the resolved PR head for a passing publication. Identical content committed after a dirty run can match; original revision/dirty provenance stays in the record. The separate publication assessment carries current applicability, coverage and problems without rewriting the local snapshot ([CLI — `publishPR`](../../skills/verify-work/verify.mjs)).

`publishRecord` checks the target head, marks `groundwork/verification` pending, and writes a publisher-owned per-run PR artifact or fallback comment. Same-run retries update that account; different runs retain history. Final status reflects the assessment, preserving a newer current-head run's verdict when an older run is republished. A publication error attempts to mark the status as error. The optional evidence/archive URL is a link, not a passing-status gate ([lib/pr-records.mjs](../../lib/pr-records.mjs)).

`viewPR` dispatches before project discovery, preparation and portal startup. It reads paginated records and the latest current-head `groundwork/verification` commit status through `listRecords`, shows tested/publication/current head identities, coverage, gaps and decisions, and labels historical records. With a current record, pending/error publication returns `2` and failure returns `1` even if the retained record passed; otherwise the newest current-head record supplies the verdict. No current record returns `2`. This read path does not execute checks, validate the reader's local environment, or import records as reusable receipts ([CLI — `viewPR`](../../skills/verify-work/verify.mjs); [lib/pr-records.mjs — `listRecords`](../../lib/pr-records.mjs)). See the [record journey](../guides/verification-records.md#verification-records) and [accepted decision](../decisions/local-first-verification.md).

### Shared PR flow

The [PR wrapper](../../pr-verification/scripts/verify.mjs) supplies an explicit repository/project directory rather than local upward discovery. It captures any supplied `PR_VERIFY_PLAN` contents, then calls `prepareProject` before loading configuration and capturing source. It reuses composition, plan-aware selection, catalogue validation, invariants, execution/receipts, source fingerprints, evidence refresh and assessment.

- Its suggested changed selection uses `HEAD^1` when available. Like local `--plan`, PR planning adds checks explicitly bound in requirements or covering their behaviours. `PR_VERIFY_CHECKS` overrides ordinary path-based selection, using a matching configured check or a synthetic check. Required, plan-bound and active invariant checks are still added; unrelated path matches do not force extras.
- Shared drivers run after PR setup. The agent handles remaining verification gaps, including unsatisfied review obligations. Valid evidence-backed review explicitly covering a requirement can satisfy it before that phase; complete coverage can skip the agent. Agent observations merge into the same assessment without erasing failures ([pr-verification/scripts/report.mjs — `verificationFrontier`, `inspectAgent`, `verdict`](../../pr-verification/scripts/report.mjs)).
- PR output defaults to the external evidence store; the reusable workflow overrides it with runner-temporary storage. PR `result.json` retains its separate envelope with a nested `verification` assessment, while each save uses `makePRRecord` to derive the shared `report.md`, including PR stage gates. It does not update the workspace's local CLI latest pointer ([wrapper](../../pr-verification/scripts/verify.mjs); [PR report adapter](../../pr-verification/scripts/report.mjs)).
- CI `publishComment` delegates to the shared artifact/comment transport after checking the PR head/request and tested head or merge-parent relationship. Job failures remain publication gaps. The workflow retains an optional evidence archive; upload availability does not determine a complete textual record's verdict ([PR report adapter](../../pr-verification/scripts/report.mjs); [.github/workflows/verify.yml](../../.github/workflows/verify.yml)).

Continue with [Final PR verification](../guides/final-pr-verification.md#final-pr-verification) for that journey.

## Feature relationships

The `pr-verification` catalogue behaviour declares direct dependencies on three existing capabilities. The [PR wrapper](../../pr-verification/scripts/verify.mjs) provides source evidence for each connection:

| Depends on | Source basis |
| --- | --- |
| `catalogue` | Loads project configuration, calls `selectChecks`, and validates catalogue references before execution. |
| `coverage` | Builds invariant requirements with `withInvariants` and assesses requirement coverage with `assess`. |
| `drivers` | Executes configured checks through the shared `runChecks` lifecycle. |

The `feature-map` capability also depends directly on `catalogue`: [renderMap](../../lib/map.mjs) reads the normalized behaviour catalogue to produce its graph and verification pointers. This relationship is recorded separately from the PR wrapper's dependencies.

`verification-records` declares two direct dependencies supported by [lib/report.mjs](../../lib/report.mjs): `coverage` supplies `assess` and the frozen requirement/review bindings retained in records, and `drivers` supplies the runner's source identity used by `reassessRun` when checking saved observations. PR orchestration consumes the shared record and publication APIs through [scripts/report.mjs](../../pr-verification/scripts/report.mjs).

`groundwork map pr-verification` displays the PR dependencies; `groundwork map verification-records` displays the record dependencies. The common `tests` check does not create edges between unrelated behaviours. Other catalogue entries currently have no recorded dependencies; this is not a claim that they are independent.

## Constraints and change impact

- **Shared contracts:** config fields/catalogue IDs, driver results, assessment statuses, and portable records are consumed by both local and PR orchestration. Changes in `lib/config.mjs`, `lib/model.mjs`, `lib/runner.mjs`, or `lib/report.mjs` need both caller paths considered; the local and PR outer `result.json` formats remain distinct. Published summaries preserve provenance but do not enter the local receipt reuse path.
- **Source boundary:** `source()` hashes project-scoped tracked and non-ignored untracked content, retaining the Git revision separately as provenance. Reusable checks can require revision matching. `runtimeExclusions` omits legacy `.verify/` and `.groundwork/{runs,latest,plans,tasks,tmp,plan.json}` runtime paths. Guides, maps, configuration, reusable scripts and supporting configs remain source inputs. Editing this map can invalidate prior applicability ([lib/runner.mjs — `source`](../../lib/runner.mjs); [lib/layout.mjs](../../lib/layout.mjs)). Ignored inputs must be explicitly declared for reuse; changing external state needs appropriate fresh observations.
- **Coverage is a binding contract:** `coverage` checks IDs/statuses/evidence, not semantic correspondence between an assertion and the task's prose. The project owns that correspondence. Preserve existing `covers` and invariant `checks` bindings; a new map link provides navigation, not a new enforcing assertion.
- **Extension points:** add project-owned commands/drivers and supported config fields rather than application logic in the shared runner. `kind` is descriptive metadata, not a separate executor. Keep catalogue `paths` and `guide` project-root-relative; Markdown links inside this map are relative to this file.
- **Cancellation boundary:** the local CLI handles SIGINT/SIGTERM through an abort controller, and `executeCommand` sends SIGTERM to the child process group on non-Windows platforms. Cleanup runs without that signal. There is no local timeout/escalation in these functions; hard termination or noncooperative processes can prevent graceful completion ([CLI — `run`](../../skills/verify-work/verify.mjs); [lib/runner.mjs — `executeCommand`, `trial`](../../lib/runner.mjs)).
